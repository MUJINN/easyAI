# 模型中转站 · 需求文档

- 版本：v0.1
- 日期：2026-09-30（M3 完成于 2026-10-09）
- 状态：M3 完成，M4 待开始
- 范围：第一版 MVP 的完整需求，含后续演进方向

## 1. 背景与目标

### 1.1 背景

市面上大模型厂商/服务越来越多：OpenAI、Anthropic、DeepSeek、Google Gemini、阿里通义、智谱、以及本地部署的 Ollama / vLLM 等。它们各有：

- 不同的 API 地址、鉴权方式、协议与参数命名；
- 不同的价格、上下文长度、能力边界；
- 不同的限流、超时、错误语义。

对上层应用和用户来说，每接一家就要写一遍适配、管一堆 Key、算一沓账单，门槛很高。

### 1.2 目标

做一个「模型中转站」：

- 上层应用/用户只需 **一套统一接口**（兼容 OpenAI 格式）即可调用任意已接入的模型；
- 所有 Key、配额、用量、路由、限流都在中转站统一治理；
- 换模型、切厂商、做负载均衡对上层**透明无感**；
- 提供管理后台，让运维/个人可视化地管理这一切。

> 一句话：**一套 Key、一个地址，调用所有模型。**

### 1.3 非目标（第一版不做）

- 不做模型训练/微调；
- 不做对话业务逻辑（那是上层应用的事）；
- 不做模型本身的数据集管理；
- 不做企业级多租户计费结算（P2 再看）。

## 2. 名词解释

| 名词 | 说明 |
|------|------|
| 上游 / 后端 (provider / backend) | 真正提供模型能力的服务商（OpenAI、DeepSeek…） |
| 通道 / 模型 (model entry) | 中转站暴露给请求者的统一模型名，映射到一个或多个后端 |
| 请求者 / 租户 (tenant) | 使用中转站的应用或个人，各自持有独立 Key |
| 路由 (routing) | 把一次请求按规则映射到某个后端模型实例 |
| 统一模型名 (unified model id) | 请求者填写的模型名称，如 `deepseek-chat`、`gpt-4o` |

## 3. 角色与场景

| 角色 | 说明 | 关键诉求 |
|------|------|---------|
| 应用开发者 | 调用统一 API 做产品 | 简单、稳定、流式 |
| 业务主 / 个人 | 管理自己的 Key、限额度、看账单 | 可视化、可控 |
| 平台运维 | 增删后端、调路由、盯监控 | 透明、可观测、易排障 |

**典型场景**：一个应用只填一个 base_url 和一个 Key，前端选「要哪个模型」，后端自动把请求转到对应厂商，并完成 token 统计与计费。

## 4. 用户故事（按优先级）

**P0 · MVP 必须**

- [US-1] 作为开发者，我用一个 OpenAI 兼容地址和 Key 发起 `chat/completions`，能拿到结果（含流式 SSE）。
- [US-2] 作为开发者，我只改请求里的模型名，就能切换到不同厂商的后端模型，无需改代码。
- [US-3] 作为管理主，我能创建/吊销访问 Key，并按 Key 设置额度（次数/金额）。
- [US-4] 作为管理主，我能配置「哪些后端模型被暴露成哪些统一模型名」。
- [US-5] 作为管理主，我能看到每个 Key / 模型的请求量、token、估算费用。
- [US-6] 作为运维，某后端厂商宕机/超限时，同一模型自动 fallback 到备用后端，请求不失败。

**P1 · 近期**

- [US-7] 作为开发者，我能一次把请求同时发到多个模型做对比。
- [US-8] 作为管理主，我能设置针对租户/Key 的并发与速率限制（限流）。
- [US-9] 作为管理主，我能设定路由策略（价格优先 / 延迟优先 / 随机 / 权重）。
- [US-10] 作为运营，我能实时查看运行日志与错误，快速定位失败请求。

**P2 · 后续**

- [US-11] 支持更多协议端点（embeddings、images、audio、完整 tool calls 转发）。
- [US-12] 用量配额自动扣减与余额提醒。
- [US-13] 多租户隔离与细粒度权限（RBAC）。

## 5. 功能需求

### FR-1 统一 API 入口
- 对外暴露统一 HTTP 服务，**兼容 OpenAI API 格式**：
  - `GET /v1/models`（列出可用模型）
  - `POST /v1/chat/completions`
  - （P2）`/v1/embeddings`、`/v1/images/generations`、`/v1/audio/*`
- 请求鉴权：`Authorization: Bearer <中转站Key>`。
- 支持 `stream=true` 的 SSE 流式输出。
- 参数兼容层：请求标准化为内部结构后转换为各后端原生格式；对各家差异（temperature 范围、内容过滤、超时语义）做映射或降级。

### FR-2 多后端接入
- 至少内置驱动：OpenAI、Anthropic、DeepSeek、Google Gemini、阿里通义、智谱、Ollama（本地）、OpenRouter（聚合后端）。
- 后端以「配置项」接入而不写死：地址、协议类型、Key、模型映射、能力元数据（上下文长度、支持的功能）。
- 支持同一厂商多套 Key（自动轮换 / 故障切换）。

### FR-3 模型目录与路由
- 维护「模型目录」：统一模型名 → 一组可用后端（含优先级、启用状态）。
- 路由策略：round-robin、权重、价格最低优先、延迟最低优先、按可用性筛选。
- fallback 链：主后端失败自动切换备用。
- 动态开关：运维可临时下架某后端，无需改动上层。
- （P1）请求级路由覆盖：模型名带命名空间/路由模式选择后端。

### FR-4 鉴权与 Key 管理
- Key 管理：创建、吊销、过期时间、额度（次数 / 金额 / token）、备注、启用状态。
- 每个 Key 绑定到租户/应用，支持独立计费维度。
- （P1）per-Key 速率与并发限额。
- （P2）RBAC 与管理操作审计。

### FR-5 用量、计费与额度
- 记录每次请求的明细：模型、后端、输入/输出 token、耗时、成功/失败/是否 fallback。
- 依据各后端单价与当前汇率估算单次与累计费用。
- 额度控制：余额/次数不足时明确报错（HTTP 402）并停止放量。
- 控制台可视化：按 Key / 租户 / 模型 / 时间维度汇总，支持导出。

### FR-6 限流与治理
- 令牌桶限流（全局 / per Key / per 后端三个层级）。
- 并发上限与排队策略。
- 自动重试（对 429 / 5xx / 网络抖动，指数退避 + 抖动）。
- fallback：主后端失败自动切备用（见 FR-3）。

### FR-7 日志与可观测
- 结构化请求日志，带 trace id，可把「这一次请求」贯穿到底层调用。
- 错误归类：参数错误、鉴权失败、后端限流、后端宕机、超时。
- 指标：QPS、成功率、平均/尾延迟、费用速率。
- （P1）控制台实时查看日志，支持按 trace id 检索。

### FR-8 管理与控制台（Web UI）
- 轻量 Web 控制台（本机 / 局域网可访问）：
  - 后端管理：增删改后端、连通性测试、模型映射。
  - Key 管理、额度配置。
  - 用量 / 账单 / 图表。
  - 路由策略配置、模型目录管理。
  - 日志与实时监控（P1）。
- （P1）只读管理 API，供上层/第三方拉取数据。

## 6. 非功能需求

| 类别 | 要求 |
|------|------|
| 兼容性 | 接口严格兼容 OpenAI 格式，官方 SDK 改 base_url + key 即可直连 |
| 性能 | 中转站增加的端到端转发延迟 < 50ms（不含后端本身）；单实例支撑数百 QPS |
| 可扩展 | 新后端 = 新增一个驱动配置，不改主链路 |
| 可用性 | 后端故障自动切换；中转站本身无状态、可水平扩展（状态入存储） |
| 安全性 | Key 加密存储、HTTPS、日志脱敏、最小权限 |
| 可观测 | 可导出 Prometheus 指标（P1） |
| 技术栈 | 倾向 Python (FastAPI) 或 Go；控制台 React 或后端渲染（待定） |
| 部署 | Docker 一键启动；支持纯本机单机运行，也可高可用部署 |

## 7. 接口草案（核心）

统一请求示例（开发者视角，兼容 OpenAI）：

```http
POST /v1/chat/completions
Authorization: Bearer sk-中转站Key
Content-Type: application/json

{
  "model": "deepseek-chat",          // 统一模型名（可带路由命名空间，P1）
  "messages": [{"role": "user", "content": "你好"}],
  "stream": true
}
```

中转站内部流程：

```
请求 → 鉴权 → 配额/限流 → 路由选择后端 → 转调到对应后端
    → 标准化回传（含 usage）→ 记账 → 响应请求者
```

返回体尽量与 OpenAI 一致（`id`、`object`、`model`、`choices`、`usage`），保证开源 SDK 零改动。

## 8. 数据模型（草案）

| 表 | 说明 |
|----|------|
| `tenants` | 租户（MVP 可先单租户） |
| `access_keys` | key hash、tenant、alias、限额、有效期、状态 |
| `providers` | 后端：name、type、base_url、auth、enabled |
| `model_entries` | 模型目录：unified_name → 多个 backend 及其权重/优先级 |
| `requests_log` | 请求全量记录（明细） |
| `usage_aggregates` | 按维度聚合的用量/费用（滚动聚合表） |

## 9. 里程碑（建议）

- ✅ **M1 规划与骨架**：仓库、网关骨架、统一接口约定、配置加载，可跑 hello world。
- ✅ **M2 首个真实后端**：接入 OpenAI + DeepSeek（+ Ollama 本地），统一 chat/completions + 流式；Key 鉴权、基础记账。
- ✅ **M3 目录与路由**：模型目录、多后端映射、fallback、简单路由策略。

- **M5 打磨**：多租户 / RBAC（P2）、更多协议与后端、Prometheus 观测、文档与示例。

## 10. 开放问题（已决策）

### 10.1 统一模型名命名规范 → ✅ 已定

采用**点分命名空间**格式：

```
模型名[:路由策略][@后端]
```

| 示例 | 含义 |
|------|------|
| `deepseek-chat` | 默认路由策略（MVP 行为） |
| `deepseek-chat:latency` | 延迟优先路由（P1） |
| `deepseek-chat:price` | 价格优先路由（P1） |
| `deepseek-chat@openai-official` | 直连指定后端（P1） |
| `gpt-4o:latency@azure-east` | 组合使用（P1） |

- 冒号 `:` 和 `@` 在 URL / 包管理领域已有先例，开发者直觉可理解。
- MVP 只解析纯模型名，忽略路由后缀，走配置中的默认策略。**格式现在就定，策略稍后实现。**

### 10.2 存储选型 → ✅ SQLite 起步 + repository 接口

- **MVP 用 SQLite**：零依赖、单容器直接跑、P0 数据量完全胜任。
- **数据访问层从第一天就写 repository 抽象接口**，后期换 Postgres 只加一个实现类。
- 切换时机：需要高可用（多实例共享存储）、单表破百万行、或 SQLite 并发写入成为瓶颈时（预计 M4-M5）。
- 无状态设计：中转站本身无状态，状态全部在 SQLite/Postgres 中，水平扩展时多实例共享同一数据库。

### 10.3 计费方案 → ✅ 统一基准币种 + 厂商原币记录 + 实时汇率

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 基准币种 | 内部统一存储为 **USD** | OpenAI/Anthropic/Google 均 USD 定价，USD 是最大交集 |
| 汇率来源 | [exchangerate-api](https://open.er-api.com/) 免费 API，启动时拉取，每 6 小时刷新 | 免费、无需 Key、覆盖常见币种 |
| 精度 | 存储用整数（USD × 10000，即 0.0001 美元精度），展示到小数点后 4 位 | 避免浮点累加误差 |
| 费用标签 | 前端所有金额旁标注 **「估算，仅供参考」** | 汇率波动 + 厂商定价变更都可能导致偏差 |
| 定价维护 | 管理员在 `providers` 表手动维护每个后端模型的 `input_price_per_1k` / `output_price_per_1k`（原币） | 厂商无标准定价 API，第一版不做自动拉取 |

### 10.4 多租户 → ✅ MVP 不做多租户，但 schema 预留

- MVP 只做 **「单主 + 多 Key」**：一个隐式默认租户，所有 Key 挂在其下。
- `access_keys` 表预留 `tenant_id` 字段（MVP 全填 `"default"`），`tenants` 表预建但只插一行。
- 需要多租户时，**改逻辑不改 schema**——这是数据库设计里最便宜的"未来保险"。
- 多租户（含 RBAC）列入 P2 里程碑。

### 10.5 控制台策略 → ✅ 分两步：先管理 API，后轻量 Web UI

| 阶段 | 内容 | 说明 |
|------|------|------|
| M1-M3 | **管理 API**（`/admin/` 路径前缀）| FastAPI 自带 Swagger UI 就是够用的控制台；curl + jq 也能管理 |
| M4 | **轻量 React SPA** | Vite + shadcn/ui，打包为静态文件由 FastAPI 托管，单容器搞定 |

- 管理 API 使用独立的 admin Key 鉴权（`Authorization: Bearer sk-admin-xxx`），与转发 API 同进程。
- 控制台本身不吃管理 API 以外的后端——不是先后两套东西，是同一套 API 渐进加 UI。
- 理由：目标用户是开发者和技术运维，不介意命令行管理。API 是本体，UI 是增值。

## 11. 验收标准（VIP）

- 一个应用用官方 OpenAI SDK，仅改 base_url + key，即可调用 ≥3 家后端模型（含本地 Ollama），流式正常。
- 切换模型名即可在后端间切换，应用侧零改动。
- 控制台可完成：加后端、加 Key、设额度、看用量与账单。
- 某后端宕机时，同一模型自动 fallback，请求成功返回。
- 全部可用 `docker compose up` 一键启动。
