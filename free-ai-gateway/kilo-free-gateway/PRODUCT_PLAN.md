# Kilo Free Gateway 产品方案

## 1. 产品方向

### 工作定位

一个本地优先的免费模型发现与接入工具：帮助开发者找到当前可用的免费模型，在本机统一接入，并在模型不可用时清楚地诊断、切换。

它不提供模型推理能力，也不承诺第三方免费模型的额度、稳定性或永久可用性。产品的核心价值是**发现、接入、比较和切换**，而不是把第三方免费额度包装成无限 API。

### 目标用户

- 想低成本体验不同模型的个人开发者。
- 使用 Claude Code、Cline、Continue 等工具，希望通过一个本地兼容入口接入模型的用户。
- 想快速验证模型能力、工具调用和客户端兼容性的开发者。

### 产品原则

1. **本地优先**：请求由用户自己的机器发往模型提供方；第一阶段不集中托管用户请求。
2. **来源透明**：显示实际模型提供方、免费状态来源、最近检查时间和已知限制。
3. **用户可控**：用户选择模型和凭据；未经明确配置不代用户切换到其他提供方。
4. **诚实表达免费**：免费状态和可用性可能变化，不宣传无限量或服务等级保证。
5. **失败可诊断**：区分本地配置错误、上游认证错误、限流、模型不可用和网络故障；避免静默重试或伪装成功。
6. **隐私最小化**：默认不保存提示词、响应内容或凭据；清楚说明请求会发送给所选上游。

## 2. 第一阶段：本地模型入口 MVP

### 阶段目标

让用户能在几分钟内完成“查看模型 → 测试模型 → 选择模型 → 接入客户端”，并在请求失败时知道问题大致发生在哪一层。

### MVP 用户流程

1. 用户启动本地应用或命令行服务。
2. 查看模型目录，了解模型名称、提供方、免费标记、能力标签、上下文信息及最近检查状态。
3. 选定模型后，运行低成本的连通性/能力测试，或发送一条用户可见的测试消息。
4. 使用本机兼容 API 地址接入客户端；客户端专属配置生成暂不在控制台提供。
5. 请求失败时查看错误类别、上游状态码、简短错误正文和下一步建议。

### 必须包含

- **本地 OpenAI 兼容 API**：保留现有 `/v1/models` 和 `/v1/chat/completions` 能力。
- **Anthropic Messages 兼容 API**：保留现有 `/v1/messages`，并明确标注兼容范围和已知差异。
- **模型目录**：显示模型 ID 与名称、上游提供方、免费状态（若上游提供）、能力标签、输入/输出模态、上下文与回复上限、简要模型说明及提示词使用提示；标注信息来源，缺失字段不臆测补全。
- **模型测试**：由用户明确触发；每张模型卡片可单独连通测试，卡片列表支持显性勾选、单选、多选和范围选择；顶部及底部操作栏可按顺序测试所选模型，并支持停止后续请求。状态、回复或通俗错误提示及可展开的技术详情显示在各自卡片中。测试前说明会向对应上游发送请求。不得在每次启动时无提示地对所有模型进行批量探测。
- **客户端接入**：文档说明兼容 API 地址和认证方式；客户端专属配置生成暂不纳入当前控制台范围。
- **错误诊断**：保留上游状态码、可读错误信息及 `Retry-After`（若上游返回）；区分 401/403、404、429、5xx 和网络错误。
- **基本安全**：默认只绑定 `127.0.0.1`；支持可选本地访问口令；不得在日志或界面明文输出 API 密钥。
- **清晰的隐私与免费说明**：提醒用户提示词会发送到所选上游，免费模型的额度、数据处理和可用性由上游决定。

### 第一阶段明确不做

- 不提供共享的云端免费 API、不汇集或转售第三方免费额度。
- 不收集用户提示词、模型响应或个人使用内容。
- 不默认自动重试 429，不绕过上游认证、地区、账户或使用限制。
- 不做复杂账号体系、团队权限、计费、配额管理或 SLA。
- 不为每个模型声称稳定可用；目录状态只是检查时点的信息。

### MVP 的产品形态

优先做成**本机服务 + 轻量 Web 控制台**，而不是先做复杂桌面应用：

- 本机服务负责模型目录、兼容 API、凭据读取和请求诊断。
- Web 控制台仅访问本机服务，用于浏览模型和手动测试。
- 命令行启动方式保留，方便开发者排障和自动化。
- UI 不收集、显示或回显客户端凭据；CLI 配置生成器应提示生成文件可能包含凭据。

如果快速验证发现 Web 控制台成本过高，可先以 CLI 和静态模型目录完成封闭试用，但模型测试和错误诊断仍应有可用入口。

## 3. 后续阶段路线

### 阶段 0：稳定当前基础（发布前）

- 修正 Windows 启动脚本的编码和工作目录问题。
- 将“只启动网关”和“发现/测试模型”分离，启动网关不应隐式产生大量上游请求。
- 规范启动输出和错误日志；确保生成配置失败时不会继续使用空模型名启动。
- 为当前 API 路由和状态码转发补充自动化测试。
- 明确凭据来源和各上游允许的使用方式；仅实现有明确授权的接入方式。

**完成标志**：干净的 Windows 环境可按文档启动；不做模型探测时不会向上游发起请求；失败时能看到明确错误。

### 阶段 1：本地模型入口 MVP

完成本方案第 2 节范围，邀请少量开发者试用。

**验证问题**：

- 用户是否能独立完成客户端接入？
- 用户是否理解“免费”是上游提供方的条件，而非产品保证？
- 目录、测试和错误信息是否足以帮助用户自行排障？
- 哪些客户端和 API 兼容问题最常阻塞使用？

### 阶段 2：模型目录与可靠切换

- 建立统一的提供方适配层，使模型目录和请求转发不依赖单一上游的数据结构。
- 为模型维护能力信息、数据来源、更新时间和已知限制；过期信息应明确标记。
- 提供用户主动触发的模型比较和任务分类推荐，不以未经验证的“最佳模型”作为承诺。
- 支持用户配置多个合法上游/BYOK 凭据，并让用户明确选择故障切换策略。
- 增加可选的备用模型路由：默认关闭或由用户配置；切换前明确展示可能的数据发送目的地变化。
- 结合上游响应头和错误正文提供建议等待时间；遵守 `Retry-After`，对非幂等或流式请求谨慎处理重试。

**阶段门槛**：先确认用户确实需要跨提供方目录与切换，再扩大适配范围；不通过隐藏重试掩盖上游故障。

### 阶段 3：可选的托管能力

只有在上游条款、授权、成本和运维责任明确后，再评估托管服务：

- 核实每个上游是否允许代理、聚合、商业使用和面向第三方提供服务。
- 明确用户数据处理、日志保留、滥用防护、内容安全和删除机制。
- 设计按用户隔离的凭据、配额和速率限制，避免依赖共享的匿名额度。
- 先以 BYOK 或企业自有上游凭据为主；只有拥有可持续且被许可的额度来源，才考虑产品补贴的免费配额。
- 在成本模型、服务边界和支持能力通过评审前，不上线集中式免费代理。

## 4. 成功指标

第一阶段优先用可验证的产品指标，不以总请求量作为唯一成功标准：

- **启动成功率**：新用户按快速开始文档能成功启动本地服务。
- **接入完成率**：用户能完成一次客户端配置并收到模型响应。
- **首次成功时间**：从启动到第一次成功请求所需时间。
- **诊断有效性**：失败案例中，用户能否根据产品提示识别本地问题还是上游问题。
- **用户理解度**：用户是否理解模型提供方、免费状态和隐私边界。
- **稳定性**：网关自身错误率与上游错误率分开统计；默认不采集请求内容。

试用阶段可通过用户自愿提交的匿名反馈收集数据；在没有明确同意和隐私设计前，不加入遥测。

## 5. 风险与应对

| 风险 | 应对 |
|---|---|
| 免费额度或上游策略变化 | 标注数据来源和更新时间；模型不可用时及时下架或显示状态变化，不承诺永久免费。 |
| 上游限制代理或共享额度 | 第一阶段本地直连；不集中共享匿名凭据；上线前核对条款和授权。 |
| 用户误以为本地运行等于数据留在本地 | 在首次使用、模型测试和配置页面说明提示词会发送给上游。 |
| 上游 429 或临时故障 | 保留错误信息，尊重等待提示；由用户控制重试和切换，避免请求风暴。 |
| 客户端协议兼容差异 | 维护明确的兼容矩阵和测试用例；避免笼统宣称完全兼容。 |
| 用户把本地端口暴露到局域网或公网 | 默认仅监听回环地址；对非回环监听给出明显警告并要求配置认证。 |
| 模型信息过期 | 展示来源和更新时间；信息不确定时标记“未知”，不推测能力或免费状态。 |

## 6. 当前实现状态与近期后续（2026-10-30）

以下状态基于当前仓库代码和文档；上游模型、额度及策略没有在本次检查中重新验证。

### 已实现

- 本机网关提供 OpenAI Chat Completions、Anthropic Messages、部分 OpenAI Responses 转发，以及模型目录、健康检查和手动模型测试入口。
- 网页控制台支持查看模型、单独测试和批量选择/测试；默认启动不自动探测模型。
- 默认仅监听本机回环地址；非本机监听要求配置 `LOCAL_KEY`，受保护的 API 路由会校验口令。
- Windows 启动脚本将启动网关与显式模型探测/配置生成分开，探测或默认模型选择失败时停止生成。
- 已提供 18 款客户端的接入指引、隐私和免费状态说明，以及 WorkBuddy Skill 下载入口。
- **SenseNova 接入（首个 BYOK 服务商）**：本机加密凭据库管理 Key；解锁后可加载 SenseNova 模型目录、连通测试，统一兼容端点按模型 ID 前缀 `sensenova/` 自动路由转发到 SenseNova 上游（OpenAI Chat Completions、Anthropic Messages、OpenAI Responses）。不做隐式故障切换，Kilo 与 SenseNova 完全隔离。
- **InternLM (书生·端砚) 接入（第二个 BYOK 服务商）**：本机加密凭据库管理 Key；解锁后可加载 InternLM 模型目录、连通测试，统一兼容端点按模型 ID 前缀 `internlm/` 自动路由转发到 InternLM 上游（OpenAI Chat Completions、Anthropic Messages、OpenAI Responses）。不做隐式故障切换，Kilo、SenseNova 与 InternLM 完全隔离。
- **SCNet 接入（第三个 BYOK 服务商）**：本机加密凭据库管理 Key；通过 `GET /api/llm/v1/models` 加载当前 Key 有权限访问的模型，统一兼容端点按 `scnet/` 模型 ID 前缀路由到 SCNet 的 OpenAI 或 Anthropic 兼容 API。

### 当前验证

- `npm test` 当前通过，覆盖本地控制台与接入文档、口令校验、BYOK Key 加密存取、无口令时拒绝非本机监听，以及手动测试输入校验。
- 这些测试主要是本地服务冒烟测试；未验证真实上游当前可用性，也没有系统覆盖上游状态码/错误正文/`Retry-After` 转发、流式协议兼容、网络失败处理和各客户端真实接入。
- Windows 启动脚本已具备预期的分支和失败检查，但仍应在干净 Windows 环境按快速开始文档完整走查。

### 近期后续：试用前加固

1. 为上游转发增加可重复的自动化测试，覆盖 OpenAI、Anthropic 和 Responses 路由，非 2xx 状态与错误正文、`Retry-After`、流式透传、网络错误及无效请求；使用模拟上游，不依赖真实模型额度。
2. 在干净 Windows 环境验证启动、停止、口令配置、模型目录刷新、手动测试及客户端配置；记录并修正文档与实际行为不一致的地方。
3. 建立小范围客户端兼容矩阵，注明已验证的客户端、协议和已知限制；尤其明确 Responses API 是部分支持，不以控制台存在配置说明替代实际兼容性验证。
4. 邀请少量用户试用，按第 4 节指标收集自愿反馈，确认首次接入、错误诊断和免费/隐私边界是否易懂；在没有明确同意和隐私设计前不加遥测。

试用结果出来前，优先修复上述稳定性、兼容性和文档问题；暂不扩展多上游自动故障切换、集中式代理或遥测。阶段 2 和阶段 3 仍按第 3 节的门槛评估。

### 多提供方前端第一版

- 首页提供 Kilo 免费模型和 BYOK 服务商入口；服务商凭据统一在本机加密凭据库管理。
- SenseNova 作为首个接入验证目标；已实现本机加密凭据库，可设置主密码、解锁/锁定、加密保存、替换和删除服务商 Key。Key 使用 `scrypt` 派生密钥和 AES-256-GCM 加密，不提供回显接口。
- **已完成 SenseNova 接入**：凭据库解锁且配置 Key 后，可加载 SenseNova 模型目录（`/api/sensenova/catalog`）、进行连通测试（`/api/sensenova/test`），以及通过统一兼容端点（`/v1/chat/completions`、`/v1/messages`、`/v1/responses`）自动路由转发请求到 SenseNova。模型 ID 以 `sensenova/` 前缀区分。
- **已完成 InternLM (书生·端砚) 接入**：凭据库解锁且配置 Key 后，可加载 InternLM 模型目录（`/api/internlm/catalog`）、进行连通测试（`/api/internlm/test`），以及通过统一兼容端点（`/v1/chat/completions`、`/v1/messages`、`/v1/responses`）自动路由转发请求到 InternLM。模型 ID 以 `internlm/` 前缀区分。
- **已完成 SCNet 接入**：凭据库解锁且配置 Key 后，可通过 SCNet 的模型查询接口读取当前 Key 可访问的模型（`/api/scnet/catalog`）、进行连通测试（`/api/scnet/test`），并将模型请求路由到 SCNet OpenAI (`/api/llm/v1`) 或 Anthropic (`/api/llm/anthropic`) 兼容接口。为避免与其他服务商模型 ID 冲突，目录模型以 `scnet/` 前缀标识。
- 初期由用户明确选择服务商和模型；不在上游失败时自动改发给 Kilo 或其他提供方。各服务商的 API Key、模型权限和使用限制由对应上游控制。

## 7. 待验证的产品决策

- 首批重点客户端是 Claude Code、Cline、Continue，还是应缩小到其中一两个。
- 模型可用性检查的频率和方式，如何避免检查本身造成不必要的额度消耗。
- 本机凭据库的备份、主密码更换和忘记密码后的恢复体验如何设计；不能仅因服务运行在本机就假设密钥绝对安全。
- 用户是否需要显式配置的自动故障切换，还是手动切换更符合透明和隐私预期。
- 多提供方接入后，产品名称和模型目录如何清楚区分产品、服务商与模型。
